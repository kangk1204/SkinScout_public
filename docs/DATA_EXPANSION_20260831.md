**권장: 위 두 줄(+304).** BindingDB 자체 큐레이션분은 CC BY 4.0으로 가장 깔끔하고,
GtoPdb는 작지만 약리학적으로 잘 정리된 데이터다. 세 번째 줄(ChEMBL 파생분)은
share-alike가 붙고 이미 있는 ChEMBL과 상당 부분 겹치므로, 넣을지는 배포 계획을 보고
따로 정할 일이다. `LICENSE_POLICY.md`의 "commercial-use-permissive" 기준에 CC BY는
들어가지만 CC BY-SA는 의무가 하나 더 붙는다.

앞서 이 문서가 "+547"이라고 쓴 것은 세 줄을 다 합친 수치다. 라이선스를 나눠 보면

### 구현했다 — `scripts/merge_runtime_activity_evidence.py`

파일 복사가 아니라 스키마 정합 작업이라, 규칙을 명시해서 짰다.

| 규칙 | 왜 |
|---|---|
| 엔드포인트를 IC50·EC50·Ki·Kd로 제한 | 검색은 pActivity를 비교한다. MIC는 비교 가능한 값이 아니다 |
| nM 외의 단위는 버린다 | 환산을 추측하면 검색 테이블에 틀린 숫자가 들어간다 |
| **검열된 측정(`>50000 nM`)은 행은 남기되 pActivity를 비운다** | "10 µM까지 안 붙었다"가 4.3점짜리 결합력으로 읽히면 사실이 뒤집힌다 |
| ChEMBL이 이미 가진 구조는 버린다 | 같은 분자가 한 표적에 대해 독립 근거 두 개로 보인다 |
| 리간드 키를 `BDB:`/`GTP:`로 네임스페이스 | 진짜 `CHEMBL...` 번호와 충돌할 수 없다 |
| 추가된 리간드의 지문을 같이 만든다 | 지문이 없으면 표적을 늘렸다고 해놓고 못 닿는다 |

실제로 돌린 결과(`--sources gtopdb`):

  dropped        :       843 rows with no fingerprint

구조 중복으로 **604,054행이 걸러졌다.** 그냥 합쳤다면 그만큼이 중복 근거가 됐을 것이다.

**첫 실행에서 이 스크립트의 버그를 잡았다.** 지문을 못 만든 리간드 778개의 행 843개가
테이블에 남아 있었다. 검색은 지문 테이블을 상대로 채점하므로 그런 행은 **아무것도
매칭할 수 없는 엣지**다 — 행 수와 표적 수만 부풀린다. 지문을 먼저 만들고 그것이 있는
행만 남기도록 고쳤고, 버린 수를 매니페스트에 적는다. 최종 테이블에는 지문 없는 분자가
0개다.

### 켰다 (2026-08-31) — 단, 미러가 아니라 검색 인덱스 쪽으로

재측정을 조건으로 걸어뒀고, 그것을 했다. 22개 패널 46쌍에서 Top10이 27 → 29로 오르고 Top30은 35 → 34로 한 쌍 내려간다(불일치 0:2, 1:0).
둘 다 유의하지 않고(p=0.5, p=1), 확실한 것은 닿을 수 있는 표적이 214개 는다는 쪽이다.
그래서 `docking.daina_recipe_index_dir`을 `data/activity_retrieval_runtime_merged_202608`
으로 옮겼다. 표적이 4,659 → **4,873**개가 된다.

`daina_evidence_dir`(미러)은 `data/chembl37` 그대로다. 레시피 채점이 켜져 있으면
실행 경로는 미러를 아예 열지 않고 인덱스만 읽는다. 두 곳을 다 바꾸면 쓰지도 않는
경로를 함께 흔드는 셈이라 그대로 뒀다.

**티어는 permissive다.** BindingDB 자체 큐레이션(CC BY 4.0)만 들어간다. GtoPdb를
더하면 표적 33개를 더 얻지만 ODbL 1.0 / CC BY-SA 4.0이 따라온다 —
`LICENSE_POLICY.md`가 인정하는 것은 CC-BY까지다. 33개를 위해 모든 실행에
share-alike 의무를 기본으로 얹지 않는다. 필요하면 `--sources gtopdb`로 다시 만든다.

측정과 그 과정에서 드러난 두 가지 결함(레시피가 배선되지 않았던 것, 실행 경로 지문이

## 제안 4 — PubChem BioAssay: 측정했고, **우리 구멍은 못 메운다**

PubChem BioAssay는 공개·재배포 가능하고 규모도 크다. 그래서 유망해 보였다.
"수십 GB를 받아보고 판단하자"는 낭비이므로, **우리가 못 닿는 그 표적들을 두고
PubChem에 직접 물었다**(`scripts/measure_pubchem_increment.py`).

상위 구간 큐레이션 대상 15개 전부를 조회한 결과:

| | 개수 |
|---|---:|
| 조회한 표적 | 15 |
| PubChem에 어세이가 하나라도 있음 | 3 |
| **측정된 활성값이 있음** | **0** |

```
P07355 ANXA2   assays=34  compounds=0  측정값 0
P17643 TYRP1   assays= 3  compounds=5  측정값 0
P09758 TACSTD2 assays= 1  compounds=0  측정값 0
(나머지 12개는 어세이 자체가 없음)
```

TYRP1에 어세이가 3개 있어서 잠깐 기대했지만, 내용은 "1 µM에서 형광 유세포 결합"
같은 **결과값 없는 스크린**이다. `Activity Value`가 없으면 pActivity로 바꿀 수 없고,
유사도 검색이 순위를 매길 근거가 되지 못한다.

**"PubChem에 데이터가 있다"와 "이 도구가 순위를 매길 수 있는 데이터가 있다"는 다르다.**
그 차이를 안 재고 도입했다면 수십 GB를 받아서 표적 0개를 얻었을 것이다.

## 제안 5 — 음성 데이터: **이미 있다.** 못 쓰고 있을 뿐이다

이 제안도 재보니 전제가 틀렸다.

| | |
|---|---:|
| train에서 pActivity ≤ 5.0 (음성 구간) 측정 | **96,734행** |
| 검색 인덱스에서 음성 측정이 있는 엣지 | 91,188 (8.6%) |
| 그 엣지가 걸린 표적 | **2,572개** |

`binary_label`에 `False`가 없는 것은 데이터가 없어서가 아니라 **정책이다.**
매니페스트가 명시한다 — *"True only for pActivity >= 5; null below 5 because
missing/comment text is never converted to negatives"*. 약하게 측정된 것을
"안 붙는다"로 바꾸지 않겠다는 뜻이고, 옳은 판단이다.

게다가 **음성 대비를 쓰는 레시피도 이미 구현돼 있다.** `union_p6_contrast`
(`negative_contrast=0.08`)는 dev 패널에서 Top30 **0.742**로, 현재 생산 baseline
0.618보다 훨씬 낫다.

그런데 생산에 못 들어간다. **15개 화합물 패널이 막고 있다.** 그 이야기는 따로
정리했다 → [`PANEL_ARBITRATION_20260831.md`](./PANEL_ARBITRATION_20260831.md)

**즉 제안 5는 데이터 문제가 아니다. 판정 기반 문제다.**

## 하지 말아야 할 것

**클러스터 전달로 커버리지를 메우려는 시도.** 측정했다.

- Route C(수용체 배경 정규화): 회수 개선 없음(19쌍, p=0.83)
- Route B(포켓 클러스터 전달): 도달 가능 표적 +1,726~2,082개뿐이고, 나머지 9,331개는
  기증자가 없어 닿지 않는다. 순위도 tm60에서만 유의하다

두 경로 모두 **근거가 있는 표적 주변을 넓힐 뿐, 근거가 없는 영역에는 들어가지 못한다.**
근본적으로 데이터 문제다.

**평가용 검색 인덱스를 전체 분할로 다시 만드는 일.** 처음에 이걸 1순위로 제안했는데,
그 산출물을 읽는 실행 경로가 없다. 평가는 `train` 전용이어야 시간 분할이 유지되므로,
전체 분할 인덱스에는 **소비자가 없다.** 빌더에 `--index-role production` 경로는
만들어 두었지만(`scripts/build_activity_retrieval_index.py`), 실행 경로를 인덱스로
옮기기 전에는 쓰지 않는다.

**1번이 나머지 전부보다 값어치가 크다.** 활성 데이터를 아무리 넣어도, 어느 레시피가
나은지 판정할 수 없으면 넣은 것을 쓸 수가 없다. 지금 32쌍짜리 패널이 256쿼리 패널의
+12.7%p를 이기고 있고, 그 판정은 **어떤 배치로도 유의해질 수 없는 4쌍 차이**다.

2번은 이미 만들어 뒀지만 1번이 끝나야 켤 수 있다 — 병합 테이블에서 검증 패널을 다시
돌려야 하는데 그 패널이 지금 판정을 못 한다. **1번과 2번은 같은 병목을 공유한다.**

## 곁다리로 확인된 것: 표준화 불가 리간드

전체 분할로 인덱스를 시험 삼아 빌드해 보니, 고유 리간드 821,833개 중 **66개(0.008%)**가
표준화에 실패한다. 대부분 `C:CC(=O)N...`처럼 고리 밖 원자에 방향족 결합이 찍힌
레코드로, RDKit이 파싱은 하지만 InChIKey를 못 만든다.

빌더는 이제 `--max-unusable-ligands`로 허용치를 명시할 수 있고, **버린 리간드를 전부
매니페스트에 이름으로 남긴다.** 기본값은 0이라 지금까지의 fail-closed 동작이 그대로다.
100만 행짜리 재빌드가 레코드 하나 때문에 멈추는 일은 없애되, 무엇을 버렸는지 모르는
일도 없게 하기 위해서다.
