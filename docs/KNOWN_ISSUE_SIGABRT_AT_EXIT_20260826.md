# 알려진 문제: 무거운 부하에서 스크립트가 종료 중 SIGABRT (2026-08-26)

## 증상

RDKit을 임포트하는 CLI 스크립트를 서브프로세스로 돌릴 때, **작업을 정상 완료하고 올바른
출력을 낸 뒤** 인터프리터 종료 단계에서 죽는다.

```
2026-08-26 18:32:29 INFO Drug warnings: 0 (max-tanimoto=0.000)
terminate called without an active exception
→ returncode -6 (SIGABRT)
```

로그의 마지막 줄이 정상 완료 메시지인 것이 핵심이다. 계산과 파일 쓰기는 끝났고,
C++ 정적 소멸자 단계에서만 실패한다.

## 왜 테스트 문제가 아니라 운영 문제인가

Snakemake는 rule의 종료 코드로 성공을 판정한다. 파이프라인 스크립트가 정상 산출물을
쓰고도 -6으로 끝나면 **rule이 실패로 처리되고 산출물이 버려진다.** 이번 세션에서
관측된 것은 전부 테스트 안이었지만, 죽는 것은 테스트가 아니라 **파이프라인 스크립트
자신**이다.

## 관측 기록

이번 세션의 전체 스위트 실행 8회에서 4개 파일이 각각 걸렸다. 특정 테스트의 문제가
아니다.

| 스크립트 | 관측 |
|---|---|
| `stage2_5` drug avoidance | 2회 |
| `prepare_performance_v2_inputs` | 1회 |
| `stage3_disagreement` | 1회 |
| `stage3_scorer_outputs` | 1회 |

공통점: 전부 RDKit을 임포트하는 스크립트를 `subprocess.run`으로 호출하고, 서브프로세스가
올바른 출력을 낸 뒤 종료 중 abort한다.

## 재현 조건

**부하가 필요하다.** 단독 반복 실행 8회는 전부 통과했고, load average 2.6에서 돌린 전체
스위트(2,655개)도 전부 통과했다. 실패는 GNINA가 전 코어를 쓰거나 `torch_cluster`가
CUDA 확장을 컴파일하는 중일 때만 나타났다.

따라서 **주문형 재현 방법이 아직 없다.**

## 지금 고치지 않은 이유

가장 흔한 완화책은 CLI 진입점에서 출력을 flush한 뒤 `os._exit(0)`으로 C++ 소멸자를
건너뛰는 것이다. 그러나 재현 없이 여러 스크립트의 종료 경로를 바꾸면
- 원인을 확인하지 못한 채 증상만 덮게 되고,
- `atexit` 정리와 버퍼 flush를 건너뛰어 **다른 종류의 데이터 손상**을 만들 수 있다.

추측으로 고치는 대신 증거를 남긴다.

## 만났을 때 확인할 것

1. 로그 마지막 줄이 정상 완료 메시지인가? 그렇다면 산출물은 유효할 가능성이 높다.
   `terminate called without an active exception`이 함께 있는지 확인한다.
2. 그 rule만 다시 돌려 본다. 부하가 낮으면 대개 통과한다.
3. 재현이 되는 조건을 찾으면 그때 `os._exit` 방식을 좁게 적용한다.
